# Find 单请求评分合同设计

## 目标

让 Find 的两类评分严格遵守固定批处理合同：标题预筛的每个已构造批次最多 100 篇且只产生一次 LLM 网络请求；最终标题+摘要评分的每个批次最多 10 篇且只产生一次 LLM 网络请求。

## 设计选择

采用最小合同修复，不重写来源收集、类别选择、动态剪枝、候选缓存或最终推荐门禁。

- 标题预筛继续保留会议/年份/类别上下文，并在各类别内部按最多 100 篇构造批次。类别尾批可以少于 100 篇。
- 每个标题批次只调用一次严格单请求接口。返回缺行、坏行、超时或协议错误时，不再二次批量请求或逐篇请求；已经合法返回的行保留，其他行使用现有本地标题排序回退。
- 最终标题+摘要评分继续按配置固定为最多 10 篇一批。每批只调用一次严格单请求接口。缺失或不合格行不再逐篇补请求，沿用现有未评分标记并禁止进入推荐列表。
- 严格单请求接口不执行 HTTP 重试、响应格式降级重试或 JSON 解析重试。一次批次调用最多对应一次 `urlopen`。
- 评分路径直接依赖客户端的网络超时，不再为这两类评分创建无法取消的 daemon 请求线程。

## 数据流与错误处理

标题批次经过一次 LLM 响应解析后分成合法行和未解决行。合法行得到 `reason_source=llm title filter`；未解决行得到 `title_filter_fallback_used`、`title_llm_missing` 和 `title_llm_retry_exhausted`，随后由现有本地排序参与后续候选选择。

标题+摘要批次经过一次响应解析后，合法行得到 `reason_source=llm abstract evaluation`；未解决行得到 `llm_retry_exhausted` 和具体失败原因，继续保留为审计记录，但不能进入用户可见推荐。

## 验证标准

- 102 篇标题在既有类别上下文中形成 `[100, 2]` 两次调用；首批故意漏行时仍不得出现第三次调用。
- 3 篇标题全部漏行时只调用一次，并全部走本地回退。
- 10 篇标题+摘要中一篇返回错误 ID 时，只调用一次，9 篇被评分，1 篇标记为未评分。
- `LLMClient.json_or_error(..., single_request=True)` 在可重试网络错误下仍只调用一次 `urlopen`。
- 完整测试套件继续通过。

## 非目标

- 不改变类别分组策略，因此 3289 篇跨 11 个类别仍可能形成多于 33 个尾批。
- 不改变模型、并发数、评分公式、推荐阈值或最终展示数量。
- 不热更新当前已经启动的 Find 进程；新合同只对修复后启动的进程生效。
